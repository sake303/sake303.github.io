# Zapier × 첫 고객: 기존 관계 없이 문제를 찾아 첫 유료 작업으로 연결하기

> 2026-10-28 · 사업 방식과 제품 방향의 벤치마킹 기록. 공개된 당사자 자료와 내 적용 판단을 구분합니다.

## 이 사례를 보는 이유

지금 중점적으로 보는 질문은 **아직 제품과 관계가 충분하지 않을 때, 무엇을 제공해 첫 공동 작업을 시작했는가?**입니다.

나는 한국인으로서 미국에 들어와 현지 인맥과 신뢰 기반을 새로 만들며 도전하고 있습니다. 기존 인맥이나 액셀러레이터의 소개 없이 상대의 업무에 접근하고, 첫 작업을 함께할 이유를 만드는 과정이 필요합니다.

Zapier는 기존 관계가 없는 상대의 공개 질문을 발견하고 먼저 연락해 유료 사용으로 이어간 사례입니다. 다만 외국인 창업자의 미국 시장 진입이나 파트너사 직원과의 공동팀 구성을 입증하는 사례는 아닙니다. 여기서는 **첫 접촉과 작은 문제 해결, 실제 사용으로의 전환**을 참고합니다.

## 창업자는 누구였고, 무엇을 갖고 있었나

Zapier는 **Wade Foster, Bryan Helmig, Mike Knoop** 세 사람이 2011년 미국 미주리주 Columbia에서 시작했습니다. 2018년 인터뷰에 소개된 역할은 각각 CEO, CTO, 제품 책임자입니다. 첫 고객 작업의 세부 분업까지 이 직함으로 소급해 단정하지는 않습니다.

- **Wade Foster:** 첫 고객에게 직접 이메일을 보내고 필요를 확인하고 가격을 제시한 사람입니다. Bryan과 직장 일 외에 프리랜스 웹 프로젝트를 수행하며 고객들의 앱 연동 요청을 접했습니다.
- **Bryan Helmig:** Wade와 프리랜스 작업을 함께했고, 서비스들을 연결하는 아이디어를 제안했습니다. 당시 VA Mortgage Center에서 근무하고 있었습니다.
- **Mike Knoop:** 기계공학을 전공했지만 이전부터 웹과 Facebook 앱을 만들었습니다. 대학원 재학 중 생활비를 지원하는 2년짜리 연구비를 확보했고, 사이드 프로젝트를 이어갔습니다.

### 공동창업자 관계도 갑자기 생긴 것은 아니다

Mike는 Hacker News 이용자의 위치를 보여주는 사이드 프로젝트에서 같은 지역의 Bryan을 발견했습니다. 같은 회사에서 일한다는 공통점도 확인하고 연락해, 여러 번 만나 함께 무언가 만들고 싶다는 생각을 나눴습니다. 이후 2011년 Startup Weekend에서 Wade를 정식으로 만나 세 사람이 함께 작업했습니다.

Mike는 그 전에 Facebook 개발자 커뮤니티의 운영자와 기고자로 활동했고 앱 개발 경험도 있었습니다. 따라서 이 사례의 ‘기존 관계 없음’은 **첫 고객 Andrew와의 관계**에 관한 표현입니다. 팀의 기술·고용·커뮤니티 기반까지 없었다는 뜻은 아닙니다.

## 첫 고객을 만났을 때의 상황

| 이미 있던 것 | 아직 부족했던 것 |
| --- | --- |
| 프리랜스 고객 업무에서 관찰한 연동 수요 | 어떤 연동에 실제 지불 의사가 있는지에 대한 확신 |
| 앱을 구현할 수 있는 공동창업자 3명 | 편리하게 사용할 수 있는 완성된 제품 |
| Startup Weekend에서 만든 시제품 | 첫 고객과의 관계, 판매·결제 운영 체계 |
| 직장·학업과 병행해 작업해온 기반 | 세 사람이 모두 전업으로 일할 여건 |

Wade와 Bryan의 프리랜스 고객들이 반복적으로 앱 연동을 요청한 것이 제품 아이디어의 배경이었습니다. 따라서 아무 문제나 찾아 해결하던 팀이라기보다, **경험으로 발견한 문제 영역을 새로운 고객에게 검증한 팀**으로 해석하는 것이 맞습니다.

YC의 창업자 소개에 따르면 첫 지원에서는 고객과 실적이 없어 탈락했고, 이후 고객과 연동을 확보해 재지원했습니다. 첫 유료 고객을 YC 입주 후 소개받았다는 설명은 사실과 맞지 않습니다.

**첫 유료 고객 확보 → YC 합격 → 공개 출시·외부 개발자 플랫폼**의 순서가 중요합니다. YC 지원 과정에서는 멘토·고객·YC 동문과의 연결도 활용했으므로, 이후 성장까지 네트워크 도움 없이 이뤘다고 해석하지 않습니다.

## 실제 기록 — 첫 이메일과 100달러 결제

### 공개된 첫 이메일

Wade는 약 8개월 전 Andrew가 게시한 PayPal–Highrise 연동 질문을 찾아 링크와 함께 연락했습니다. 실제 이메일의 질문 두 문장은 다음과 같습니다.

> Have you found a solution for this yet?
>
> If you have, what did you do?

이미 해결했는지, 해결했다면 어떤 방법을 썼는지 묻는 내용입니다. 이어서 아직 미해결이라면 개발자를 고용하거나 직접 코딩하지 않고 처리하는 서비스에 관심이 있는지 물었습니다. 첫 이메일에는 가격이나 미팅 요청이 없었습니다. 위 인용은 원문의 일부이며, 전체 메일은 아래 출처에서 확인할 수 있습니다.

### 후속 대화에서 결제까지

| 단계 | 공개 기록으로 확인되는 내용 |
| --- | --- |
| 3일 뒤 회신 | Andrew는 원래 문제를 해결했지만 해당 연동을 실제로 만들었는지 궁금해했습니다. 당시 팀은 아직 만들지 않았습니다. |
| 현재 필요 발견 | 대화에서 Wufoo–AWeber 연동이 필요하다는 것을 알게 됐습니다. |
| 구현과 전달 | 팀이 며칠 만에 연동을 만들고 준비됐다고 이메일로 알렸습니다. |
| 가격 질문과 수락 | Andrew가 가격을 묻자 Wade는 베타 이용료 100달러를 제시했고, Andrew가 수락했습니다. |
| 결제 | 사이트의 결제 수단이 없어 개인 PayPal로 받았습니다. |
| 사용 지원 | 이후 몇 주간 설정, 필터 기능 추가, Skype 사용 안내를 제공했습니다. |

**구현 → 가격 질문 → 베타 결제**의 순서입니다. 선결제 파일럿이나 100달러 개발 계약으로 해석하지 않습니다. 후속 이메일 전체·통화 전문·대화 횟수는 공개되지 않았으며, 새 필요를 발견한 질문 문구를 만들어 넣지 않습니다.

Andrew는 화면 공유로 본 초기 제품이 사용하기 어려웠지만 자신의 불편을 해결했기 때문에 계속 쓰고 싶었고, 팀이 개발을 이어가도록 자신이 결제를 요구했다고 설명합니다. 이 고객이 먼저 가격을 물었다는 사실을 모든 고객에게 기대할 수는 없습니다.

## 각자가 제공하고 얻은 것

위 기록을 바탕으로 정리한 역할입니다.

| 참여자 | 제공한 것 | 얻은 것 |
| --- | --- | --- |
| Zapier 팀 | 필요한 연동 개발, 설정과 사용 지원, 추가 기능 | 실제 업무 요구, 사용 피드백, 첫 유료 고객 |
| Andrew | 현재의 필요 설명, 초기 제품을 써보는 시간, 결제 | 필요했던 앱 연동과 직접적인 사용 지원 |

상대는 초기 고객입니다. 앱 공급사와의 공동판매 계약이나 공급사 내부 인력 투입이 확인된 관계는 아닙니다.

## 고객 작업이 파트너 플랫폼으로 바뀐 지점

Mike의 인터뷰에 따르면 초기 50~60개 앱 연동은 세 창업자가 직접 만들었습니다. 출시 뒤에는 지원하지 않는 앱의 요청이 계속 들어왔고, 세 사람만으로 모두 구현하거나 채용으로 해결하기 어려웠습니다. 그래서 외부 개발자가 연동을 만들 수 있는 플랫폼이 필요해졌습니다.

여기서 참고할 순서는 **사용자의 구체적인 연동 문제를 직접 해결 → 반복 수요와 구현 한계 확인 → 외부 앱 개발자의 참여를 가능하게 함**입니다. 처음부터 앱 공급사와 공동팀을 구성해 첫 고객을 확보한 사례로 보지는 않습니다.

출처: [Mike Knoop의 제품·설계 인터뷰, 2019년](https://www.ycombinator.com/blog/mike-knoop-on-product-and-design-processes-for-remote-teams-with-kevin-hale/)

## 내 paid pilot 적용안 — 실제 Zapier 대화와 구분

아래는 내 상황에 맞춘 **제안 방식과 문장 틀**입니다. Zapier의 실제 발언이나 이미 합의된 고객 조건이 아닙니다. 대괄호는 실제로 확인·결정한 내용으로 채웁니다.

### 1. 확인한 문제 하나에서 대화 시작하기

> [구체적인 업무]에서 [불편]이 있다고 말씀하셨는데, 지금은 어떻게 처리하고 계신가요?

이미 콜에서 들은 내용은 다시 묻지 않습니다. 아직 모르는 발생 빈도, 담당자, 도움이 될 결과만 확인합니다. 최초 문제가 해결됐다면 현재 남은 필요를 듣되, 내가 해결할 수 있는지 따로 판단합니다.

### 2. 실제 작업 한 건으로 범위 좁히기

> 최근 작업 한 건을 기준으로 입력 자료와 최종 결과를 같이 볼 수 있을까요? 제가 맡을 수 있는 부분과 필요한 접근 권한을 확인해보겠습니다.

관심 표현과 함께 실제 자료를 볼 시간, 담당자의 참여를 확인합니다. 이 단계에서 어떤 입력으로 어떤 결과를 만들지 구체화합니다.

### 3. 구현 전에 유료 범위 제안하기

> 이번에는 [업무 하나]를 대상으로 [기간] 동안 [결과물]을 제공하는 유료 파일럿을 제안드립니다. 비용은 [금액]이고, [상대가 제공할 자료·시간]이 필요합니다. 완료 여부는 [확인 기준]으로 함께 판단하면 좋겠습니다.

가격을 정할 근거가 생기면 내가 먼저 제안합니다. 고객이 가격을 물을 때까지 기다리거나, Zapier의 100달러를 가격 기준으로 삼지 않습니다. 공개 질문은 구매 의사가 아니며, 무료 선개발이 반드시 적합한 것도 아닙니다.

| 합의 항목 | 정할 내용 |
| --- | --- |
| 범위 | 이번에 해결할 업무와 제외할 작업 |
| 결과·기간 | 실제로 받아 사용할 결과물과 제공 일정 |
| 상대의 참여 | 자료·접근 권한·피드백 담당자와 필요한 시간 |
| 대가 | 비용 부담 주체, 금액, 지급 시점 |
| 판정·후속 | 완료·효용 확인 기준과 후속 계약을 논의할 조건 |

### 4. 전달 후 실제 사용과 다음 계약 확인하기

결과를 전달한 뒤 업무에서 사용되는지, 무엇이 사용을 막는지 확인합니다. 수정은 합의한 범위에 맞춰 진행하고, 추가 작업과 지속 사용은 별도 조건을 정합니다. 다음 고객에게 재사용할 연동·데이터 처리·업무 지식도 구분해 남깁니다.

**적용 판단:** Zapier에서 참고할 것은 구체적인 필요를 실제로 쓸 수 있는 결과로 연결한 과정입니다. 내 paid pilot에는 작업 전 범위·대가 합의를 더합니다. 이를 통해 반복 계약이나 파트너 관계가 만들어지는지는 앞으로 검증할 가설입니다.

## 제품 방향에 적용해볼 해석

기존 도구 사이의 구체적인 연결 하나를 먼저 해결하고, 실제 사용에서 드러난 조건을 제품에 반영하는 방식을 참고합니다. 내가 지향하는 데이터·맥락 연결도 우선 **어떤 입력을 받아 어떤 결과를 누구에게 제공할지** 좁혀 확인할 수 있습니다.

단, 앱 간 데이터 이동의 효용과 실무자의 의사결정 개선은 다른 문제입니다. 내 제품이 의사결정을 돕는다는 주장은 별도로 검증해야 합니다.

## 내 단계와의 차이 및 미확인

- 기존 관계 없는 상대에게 먼저 연락한 과정은 확인되지만, 창업팀 전체가 인맥이나 지원망 없이 출발했다는 근거는 아닙니다.
- 개발 가능한 공동창업자 3명과 초기 시제품이 있었습니다. 나와 에이전트의 실행 역량·책임 범위와 동일하게 볼 수 없습니다.
- 한국인 창업자로서 겪는 언어·문화·현지 신뢰 형성의 조건은 이 사례에서 확인되지 않습니다.
- 첫 고객과의 작업 시간, 원가, 계약 세부 조건, 장기 유지·수익성은 위 자료만으로 확인되지 않습니다.
- 파트너사 직원과 함께 현장 문제를 해결하는 공동팀 구조는 별도로 사례를 찾아야 합니다.

**현재 판단:** 첫 접촉과 작은 유료 작업으로의 전환을 우선 참고합니다. 내 출발 조건 전체에 맞는 사례로 단정하지 않습니다.
